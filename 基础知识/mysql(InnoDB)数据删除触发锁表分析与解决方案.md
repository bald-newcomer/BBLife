# MySQL InnoDB DELETE 操作锁表分析与解决方案

首先需要明确，InnoDB默认使用**行级锁**。通常所说的“锁表”指以下三种情况：
1.  **真正的表级锁**
2.  **行锁升级**（锁定的行数过多，超出系统内存）
3.  **“效果上”的锁表**（因锁定了大量行或关键间隙，导致其他事务被严重阻塞，**这是生产中最常见的问题**）

---

## DELETE 操作触发“锁表”的四大场景分析

| 场景 | 触发原因与原理 | 导致后果 |
| :--- | :--- | :--- |
| **1. 无索引或索引失效的全表扫描** | `DELETE`的`WHERE`条件**无法使用索引**，必须全表扫描。扫描到的每一行（即使不删除）都会被加锁。 | **实质上锁定了表的绝大部分甚至全部范围**，其他事务的插入、更新、删除操作均被阻塞。**最常见、最危险。** |
| **2. 锁资源耗尽** | 大批量删除时，锁占用的总内存超过 `innodb_buffer_pool_size` 的某个比例。 | 报错：`ERROR 1206 (HY000): The total number of locks exceeds the lock table size`。 |
| **3. 事务隔离级别下的间隙锁** | 在默认的 **`REPEATABLE READ`** 隔离级别下，为防幻读，InnoDB不仅锁住要删除的行，还会锁住这些行周围的**间隙**。 | 阻塞了该**范围内所有新的插入操作**，即使插入的ID并不存在。对高并发插入的表影响巨大。 |
| **4. 大事务与长事务** | 一个事务中执行了巨量`DELETE`但**没有及时提交**。根据**两阶段锁协议**，所有锁直到**事务提交时才会释放**。 | 该事务长时间持有巨量行锁，阻塞其他所有相关操作，并可能拖垮整个数据库性能。 |

## 解决方案

### 1. 删除过程，务必使用索引
使用索引后，InnoDB可以直接定位到目标数据行，只对需要删除的行加锁，避免了全表扫描的灾难性后果。

``` sql
-- 先分析执行计划，确认type不是ALL（全表扫描）
EXPLAIN DELETE FROM t_order WHERE create_time < '2023-01-01';
```

### 2. 避免锁耗尽与长事务：分批删除
使用limit限制一次性删除得数据，避免内存超量

* 锁粒度小：每次只锁定少量行，瞬间释放。
* 事务短：避免产生长事务。
* 可中断：如果中途出错或需要停止，影响范围小。
* 减少主从延迟：对于主从架构，小事务能减少Binlog一次性写入量。

### 3. 使用专业归档或者清理工具：pt-archiver
对于归档或清理历史数据，Percona Toolkit中的 pt-archiver 工具是行业标准。

``` shell
# 它会自动、安全地分批将数据归档或删除
pt-archiver \
  --source h=localhost,D=test,t=t_log \
  --purge \
  --where "created_at < '2023-01-01'" \
  --limit=1000 \
  --commit-each \
  --no-check-charset
```

### 4. 重构表
如果需要删除表中超过30%-50%的数据，上述分批删除可能依然很慢（因为要扫描和写入Undo Log）。

此时，更高效的做法是创建一个新表，只导入需要保留的数据。

``` sql
-- 1. 创建新表结构（和原表一样）
CREATE TABLE t_log_new LIKE t_log;

-- 2. 将需要保留的数据插入新表
INSERT INTO t_log_new SELECT * FROM t_log WHERE created_at >= '2023-01-01';

-- 3. 原子性操作，重命名替换原表（会短暂锁表，但速度极快）
RENAME TABLE t_log TO t_log_old, t_log_new TO t_log;

-- 4. 确认无误后，再择机删除旧表
DROP TABLE t_log_old;
```
