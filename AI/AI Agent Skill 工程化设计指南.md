# AI Agent Skill 工程化设计指南

> 从"让 Agent 能做更多事"到"让 Agent 按规范做事"——构建可预测、可追溯、可审计的 AI 驱动开发流水线

---

## 一、什么是 Skill 工程化

### 1.1 问题背景

当前 AI Agent 开发面临三大挑战：

- **不可预测**：Agent 自由发挥，输出质量不稳定
- **不可追溯**：需求到代码的链路断裂，无法验证覆盖度
- **不可审计**：流程黑盒，无法定位问题环节

传统做法是"给 Agent 更多工具"，但这只解决了"能不能做"，没解决"做得对不对"。

### 1.2 Skill 工程化的定义

**Skill 工程化**是将 AI Agent 的能力封装为可组合、可编排、可验证的标准化技能单元，通过状态机驱动、Schema 约束、锚点追溯等机制，将 Agent 从"自由发挥的工具"转变为"按软件工程规范执行的可信流水线"。

### 1.3 核心理念

| 传统 Agent | Skill 工程化 Agent |
|-----------|------------------|
| 能力放大器（能做更多事） | 行为约束器（按规范做事） |
| 自由发挥，输出随机 | 流程驱动，输出可控 |
| 工具集合，无流程 | 技能编排，有闭环 |
| 单次执行，无状态 | 多步协作，有状态 |
| 黑盒操作，难追溯 | 锚点串联，可审计 |

## 二、七大核心设计模式

### 模式 1：能力原子化（Skill Atomicity）

**原则**：每个 Skill 是自包含的能力包，按需加载，不依赖其他 Skill 的内部实现。

**为什么这样做**：
- 上下文窗口有限（通常 128K-1M tokens），无法同时加载所有指令
- 每个 Skill 可独立测试、独立版本化、独立分发
- 松耦合：Skill 之间通过状态机协作，不通过文件依赖

**实现要点**：
```
skill/
├── SKILL.md              # 指令文档（做什么、怎么做）
├── references/           # 数据规范（可选）
│   └── specification.yaml
└── templates/            # 模板文件（可选）
    └── *.template
```

**判断标准**：
- SKILL.md 不超过 500 行
- 不需要读取其他 Skill 就能理解自己该做什么
- 可以用 mock 输入单独测试

### 模式 2：状态机确定性编排（State Machine Orchestration）

**原则**：流程不是写在代码里的硬编码逻辑，而是由外部状态机驱动的可声明、可持久化、可恢复的状态图。

**为什么这样做**：
- Skill 之间不直接调用，避免隐式耦合
- 状态机负责"下一步去哪"，Skill 负责"当前步做什么"
- 支持跨会话恢复（会话中断后从状态文件恢复）

**核心概念**：
```
状态机
├── Activity（活动）：流程中的一个阶段
├── Capability（能力）：活动内的具体任务，对应一个 Skill
├── Transition（转移）：条件分支（如评审通过/失败）
├── ReworkTarget（返工目标）：失败时回退到哪个活动
└── ExecutionHint（执行提示）：heavy/light/interactive
```

**状态文件**：
```yaml
# .state-binding.yaml
currentActivity: design
completedActivities: [collect, clarify]
verdicts:
  - activity: review
    verdict: fail
    reworkTarget: design
```

### 模式 3：Schema 驱动产物管理（Schema-Driven Artifacts）

**原则**：产物路径、模板、依赖关系不由 Skill 硬编码，而由 Schema 指令动态获取。

**为什么这样做**：
- 产物路径和模板会动态变化（新增阶段、调整结构）
- 外置 Schema 后，所有引用它的 Skill 自动适配
- Schema 是数据驱动的，Skill 是逻辑驱动的，两者解耦

**实现方式**：
```bash
# Skill 通过 CLI 获取产物约束
cli-tool instructions <artifact> --json
```

返回：
```json
{
  "outputPath": "docs/design.md",
  "template": "templates/design.template",
  "dependencies": ["spec.md", "requirements.md"]
}
```

### 模式 4：评审闭环质量保障（Review-Rework Loop）

**原则**：每个阶段产出后必须经过独立评审，评审失败自动回流，不允许"带病前进"。

**为什么这样做**：
- 不信任 Agent 的自我判断，用独立评审形成对抗性验证
- 评审 Skill 与生产 Skill 分离，避免"既当运动员又当裁判"
- 失败自动回退，确保质量问题不累积

**评审类型**：
| 类型 | 说明 | 示例 |
|------|------|------|
| 规格合规 | 是否符合上游规格 | 设计是否覆盖所有需求 |
| 测试覆盖 | 是否覆盖关键场景 | 测试用例是否完整 |
| 代码质量 | 是否符合编码规范 | 是否有安全漏洞 |
| 架构一致 | 是否符合架构约束 | 是否违反分层原则 |

**评审结论**：
- `pass`：通过，继续推进
- `fail`：失败，回退到 reworkTarget
- `conditional_pass`：带条件通过，遗留问题需记录

### 模式 5：锚点跨阶段追溯（Anchor-Based Traceability）

**原则**：用稳定的 ID 锚点贯穿 spec → design → code → test，任何阶段的任何产物都能追溯到上游需求。

**为什么这样做**：
- 自然语言追溯不可机器解析（"这个设计对应那个需求"无法自动校验）
- 锚点 ID 是机器可解析的，可以自动检查覆盖率
- 锚点是稳定的，不会因为描述变化而失效

**锚点类型**：
| 类型 | 格式 | 用途 |
|------|------|------|
| 需求旅程 | `JR-<FEATURE>-<X>` | 端到端用户旅程 |
| 场景 | `SC-<X>` | 具体用例的输入/输出/异常 |
| 验收标准 | `AC-<X>` | 测试用例锚点 |

**追溯链**：
```
spec.md
  §3.1 JR-A: 用户登录旅程
    ↓
design.md
  §4.1 > 实现 JR-A
  调用链：AuthController → AuthService → UserRepository
    ↓
tasks.md
  Task 1: 修改 AuthService.java
  Task 2: 修改 AuthController.java
    ↓
testdesign.md
  AC-1: 登录成功测试
  trace.journeys: [JR-A]
```

### 模式 6：知识底座结构化消费（Knowledge Base Consumption）

**原则**：Agent 不应自由搜索代码库，而应通过结构化的知识索引按需消费。

**为什么这样做**：
- Agent 的搜索不可控（可能 grep 到无关代码，浪费上下文）
- Agent 的搜索重复（每次会话都重新搜索同样的内容）
- 知识底座是预索引的，查询一次即可，避免重复劳动

**知识消费流程**：
```bash
# 按阶段消费知识索引
knowledge-cli consume --stage design --keywords "用户,登录" --json
```

返回四类结果：
| 类型 | 含义 | Agent 行为 |
|------|------|-----------|
| `must_read` | 必读原文 | 必须读取 |
| `gateway_actions` | 需通过 CLI 进一步查询 | 按指引调用 CLI |
| `browse` | 可选精读的目录 | 根据 summary 判断是否需要 |
| `gaps` | 知识缺口 | 记入 knowledge-gaps，降级继续 |

### 模式 7：渐进式披露与三层分离（Progressive Disclosure）

**原则**：Skill 的指令、数据、模板三层分离，按需加载。

**三层分离**：
| 层 | 文件 | 职责 | 变更频率 |
|----|------|------|---------|
| 逻辑层 | SKILL.md | 做什么、什么顺序、什么策略 | 低 |
| 数据层 | references/*.yaml | 创建什么、哪些必须、生成策略 | 中 |
| 模板层 | templates/*.template | 产物长什么样 | 高 |

**为什么这样做**：
- SKILL.md 保持精简（<500 行），不膨胀
- 新增产物只改 YAML，不改 SKILL.md
- 不同项目可用不同的 YAML 规范

## 三、九大模块职责分工

### 模块总览

```
┌─────────────────────────────────────────────────────────────┐
│  SKILL.md（指令文档）    --  告诉你"做什么"                   │
│  CLI 工具（执行引擎）    --  替你"做出来"                     │
│  Schema（产物约束）      --  规定"产物长什么样"               │
│  状态机（编排中枢）      --  决定"下一步去哪"                 │
│  状态文件（状态快照）    --  记录"走到哪了"                   │
│  知识底座（结构化索引）  --  回答"去哪找信息"                 │
│  项目上下文（项目配置）  --  注入"在哪个项目"                 │
│  任务包（多仓打包）      --  封装"这个任务涉及哪些仓"         │
│  锚点系统（追溯链）      --  串联"需求→设计→测试"             │
└─────────────────────────────────────────────────────────────┘
```

### 各模块详解

#### 1. SKILL.md — 指令文档

**做什么**：
- 用 Markdown 描述 Agent 在当前阶段应该做什么、读什么、写什么、何时停止
- 定义触发条件（frontmatter 的 `description`）
- 定义执行边界（Only Output、Stop If）

**为什么不直接让 CLI 做所有事**：
- Skill 是纯指令文档，没有执行能力
- Skill 不能调用 Skill，松耦合通过状态机实现
- Skill 是"声明"，CLI 是"动作"

#### 2. CLI 工具 — 执行引擎

**职责拆分**：
| CLI | 职责 | 为什么不合并 |
|-----|------|------------|
| 产物管理 CLI | 产物管理、知识消费、Schema 引擎 | 产物和知识是核心数据层 |
| 状态机 CLI | 状态机推进、状态持久化 | 状态机是编排中枢 |
| 工单 CLI | 外部工单系统（需求/缺陷查询） | 外部系统集成 |
| 文档校验 CLI | Markdown 产物校验 | 文档校验是独立能力 |
| 代码平台 CLI | 代码仓库操作（MR、分支） | 代码平台操作 |
| 认证 CLI | 认证凭据管理 | 安全敏感，必须隔离 |

#### 3. Schema — 产物约束

**做什么**：
- 定义每个产物的 outputPath（写到哪里）
- 定义每个产物的 template（长什么样）
- 定义每个产物的 dependencies（前置依赖）

**为什么不硬编码在 SKILL.md**：
- 产物路径和模板会动态变化
- 外置 Schema 后，所有引用它的 Skill 自动适配

#### 4. 状态机 — 编排中枢

**做什么**：
- 维护当前流程的状态图
- 驱动流程推进（next → 调度执行 → confirm）
- 处理条件分支（verdict = pass/fail/conditional_pass）
- 持久化状态到状态文件

**为什么不让 Skill 互相调用**：
- Skill 互相调用会形成隐式耦合
- 状态机是显式编排，支持持久化和恢复

#### 5. 状态文件 — 状态快照

**做什么**：
- 记录当前流程的完整状态
- 支持跨会话恢复
- 存储执行模式调度决策

**为什么不把状态存在 Skill 里**：
- Skill 是无状态的
- 状态必须持久化到外部文件

#### 6. 知识底座 — 结构化索引

**做什么**：
- 预索引项目的架构文档、代码仓库、guidelines
- 通过结构化查询返回阅读计划

**为什么不让 Skill 自由搜索代码库**：
- Agent 的搜索不可控、重复
- 知识底座是预索引的，查询一次即可

#### 7. 项目上下文 — 项目配置

**做什么**：
- 注入项目级上下文：技术栈、架构、约束、命名规范
- 所有 Skill 执行时自动读取

**为什么不把项目上下文写在每个 Skill 里**：
- 每个 Skill 都写一遍会重复且不一致
- 项目上下文是单一真相源

#### 8. 任务包 — 多仓打包

**做什么**：
- 封装一个任务涉及的所有仓库
- 用于任务分发和代码执行时，知道该去哪个仓做什么

**为什么不直接在 Skill 里硬编码仓库列表**：
- 一个需求可能涉及多个仓库
- 每个任务涉及的仓库不同

#### 9. 锚点系统 — 追溯链

**做什么**：
- 用稳定的 ID 锚点贯穿 spec → design → test
- 支持自动校验覆盖率

**为什么不用自然语言追溯**：
- 自然语言追溯不可机器解析
- 锚点 ID 是机器可解析的

## 四、Skill 拆分粒度判断标准

### 核心问题

既然 Skill 之间有依赖、无法独立执行，那是否有必要拆成多个 Skill？

### 关键区分

**Skill 的"独立性"指指令独立，不是执行独立。**

| 维度 | 是否独立 | 含义 |
|------|---------|------|
| 指令 | 独立 | Skill 不需要读其他 SKILL.md 就能理解自己该做什么 |
| 执行 | 不独立 | Skill 需要上游产物、状态文件、Schema 指令才能跑 |
| 加载 | 独立 | 状态机按需只加载当前步骤的 Skill |
| 测试 | 独立 | 可以用 mock 输入单独测试一个 Skill |

### 5 个拆分标准

用以下 5 个标准判断是否需要拆分。**全部不满足时才应该合并。**

1. **上下文是否装得下？**
   - 合并后总行数 > 500 行，必须拆
   - 合并后 bundled resources 总量过大，必须拆

2. **执行模式是否不同？**
   - heavy（复杂推理）vs light（直接执行）vs interactive（用户交互）
   - 不同模式必须拆

3. **是否跨流程复用？**
   - 同一个 Skill 被多个流程复用
   - 复用必须拆

4. **是否需要并行执行？**
   - 如多个独立 subagent 并行审查
   - 并行必须拆

5. **失败后是否需要独立重试？**
   - 评审闭环 fail 后，只回退并重新执行当前 Skill
   - 需要独立重试必须拆

### 判断流程

```
开始 → 检查标准 1（上下文）→ 满足？→ 是 → 必须拆
                              → 否 → 检查标准 2（执行模式）→ 满足？→ 是 → 必须拆
                                                              → 否 → 检查标准 3（复用）→ ...
                                                                              → 全不满足 → 应该合并
```

## 五、规格与实现分离模式

### 问题

如何防止 Agent 混淆"做什么"（spec）和"怎么做"（code），确保需求可追溯、可验证？

### 三层产物

| 层 | 产物 | 比喻 | 定义什么 | 不包含什么 |
|----|------|------|---------|-----------|
| 合同层 | requirement-spec.md | 甲方合同 | 对外契约、验收旅程 | 内部类名、技术选型 |
| 施工图层 | requirement-design.md | 施工图纸 | 内部实现、调用链、技术选型 | 对外契约重复 |
| 任务单层 | tasks.md | 工人任务单 | 单仓文件级任务、依赖顺序 | 跨仓协调 |

### 锚点呼应

```
spec.md
  §3.1 JR-A: 用户登录旅程
    ↓
design.md
  §4.1 > 实现 JR-A
  调用链：AuthController → AuthService → UserRepository
    ↓
tasks.md
  Task 1: 修改 AuthService.java
  Task 2: 修改 AuthController.java
    ↓
testdesign.md
  AC-1: 登录成功测试
  trace.journeys: [JR-A]
```

### 为什么这样分层

1. **防止 Agent 混淆"做什么"和"怎么做"**
   - spec 只说"创建用户返回 201"，不管底层用 Redis 还是 DB
   - 换技术方案只改 design，不动 spec

2. **支持独立校验**
   - spec 校验：需求是否完整、无歧义
   - design 校验：是否每个 JR- 都有实现呼应
   - code 校验：是否实现了 design 中的所有调用链
   - test 校验：测试用例是否覆盖所有 SC-

3. **支持多仓场景**
   - design 负责跨仓协调
   - 每个仓库各自有 tasks.md

4. **支持变更追溯**
   - 合同变了（spec 改）→ design 必须跟着改
   - 方案变了（design 改）→ spec 不变
   - 任务调整（tasks 改）→ spec 和 design 不变

## 六、知识体系设计

### 知识生命周期

```
1. 知识构建（初始化流程）
   ├── 项目信息收集
   ├── 文档下载
   ├── 仓库克隆
   └── 知识逆向生成 → knowledge-base/ 目录

2. 知识索引（知识管理 CLI）
   ├── 检查知识库完整性
   └── 查看特性树结构

3. 知识消费（知识消费 CLI）
   ├── 按阶段（stage）返回阅读计划
   ├── must_read / gateway_actions / browse / gaps
   └── 被各阶段 Skill 消费

4. 知识增量（Story 分解）
   ├── 产出特性树增量
   └── 归档时合并回 knowledge-base

5. 知识逆向（文档生成 Skill）
   └── 从代码仓库逆向生成 spec.md 和 design.md
```

### 知识目录结构

```
knowledge-base/
├── index.md                          # 知识索引总入口
├── architecture/
│   ├── codebase/
│   │   └── code-repository-index.yaml  # 代码仓库索引
│   └── feature-tree/                   # 特性树
├── guidelines/                         # 开发指导规范
│   └── **/frontend-design.md           # 前端设计指导等
└── ...
```

## 七、实施路线图

- [ ] 实现评审闭环（verdict + reworkTarget）

- [ ] 实现 Schema 引擎（产物路径、模板、依赖）

### 阶段 4：知识底座（2-3 周）

- [ ] 实现知识消费（consume CLI）
- [ ] 实现知识逆向（从代码生成文档）

### 阶段 5：锚点追溯（1-2 周）

- [ ] 实现锚点规范（JR-/SC-/AC-）

### 阶段 6：多仓支持（2-3 周）

- [ ] 实现任务包（多仓打包）
- [ ] 实现跨仓协调（design 层）

## 八、最佳实践

### 8.1 Skill 设计

- **单一职责**：每个 Skill 只做一件事
- **自包含**：不依赖其他 Skill 的内部实现
- **可测试**：可以用 mock 输入单独测试
- **可复用**：尽量跨流程复用

### 8.2 状态机设计

- **显式编排**：Skill 之间不直接调用
- **持久化**：支持跨会话恢复
- **条件分支**：支持 verdict 驱动的转移
- **失败隔离**：支持独立重试

### 8.3 Schema 设计

- **数据驱动**：产物路径和模板外置
- **版本化**：Schema 可独立版本化
- **可适配**：不同项目可用不同的 Schema

### 8.4 知识管理

- **预索引**：不要自由搜索
- **结构化**：用结构化查询替代 grep
- **增量更新**：支持知识增量

### 8.5 锚点追溯

- **机器可解析**：用 ID 替代自然语言
- **跨阶段**：锚点贯穿 spec → design → test
- **自动校验**：支持自动检查覆盖率

## 九、常见问题

### Q1：Skill 之间有依赖，为什么要拆成多个？

**A**：Skill 的"独立性"指指令独立，不是执行独立。拆分解决的是上下文管理问题，不是执行顺序问题。状态机编排解决"执行顺序"，Skill 拆分解决"上下文管理"。

### Q2：为什么不把状态机逻辑写在 Skill 里？

**A**：Skill 互相调用会形成隐式耦合（A 调 B，B 调 C，链路不可见）。状态机是显式编排，支持持久化和恢复。

### Q3：为什么不直接让 Agent 搜索代码库？

**A**：Agent 的搜索不可控（可能 grep 到无关代码，浪费上下文），且重复（每次会话都重新搜索）。知识底座是预索引的，查询一次即可。

### Q4：为什么需要锚点追溯？

**A**：自然语言追溯不可机器解析（"这个设计对应那个需求"无法自动校验）。锚点 ID 是机器可解析的，可以自动检查覆盖率。

### Q5：如何判断 Skill 拆分粒度？

**A**：用 5 个标准判断：上下文是否装得下、执行模式是否不同、是否跨流程复用、是否需要并行执行、失败后是否需要独立重试。全部不满足时才应该合并。

## 十、总结

Skill 工程化的核心设计哲学是：

> **用状态机编排流程、用锚点追溯需求、用评审闭环保障质量、用知识底座约束搜索、用 Schema 驱动产物——将 Agent 从"自由发挥的工具"转变为"按软件工程规范执行的可信流水线"。**

这不是让 Agent 更强大，而是让 Agent 更**可预测、可追溯、可审计**。
